# Project Code Audit

Комплексный аудит кодовой базы по стандартам качества и проектной документации.

## Phase 0: Определить область и контекст

Сначала прочитай `CLAUDE.md` в корне проекта — он является точкой входа для всего аудита:

- **Раздел `## Audit scope`** — содержит список директорий для сканирования и документов для проверки. Если раздел есть — использовать его. Если нет — запустить `find . -name "*.ts" -o -name "*.tsx" | grep -v node_modules` и сканировать всё что найдено.
- **Раздел `## Safety-critical constraints`** — список критических ограничений для проверки в категории 🔴. Если раздела нет — пропустить эту категорию.
- **Раздел `## Known constraints`** — дополнительные ограничения, нарушение которых нужно выявить.
- **Раздел `## Development conventions`** — правила именования и структуры для категории 🏛️.

## Phase 1: Загрузить документацию проекта

Прочитать документы, указанные в `## Audit scope` → `Документация для проверки на противоречия`. Они являются авторитетным источником: что написано там — должно быть реализовано в коде.

Также прочитать:
- `STATUS.md` (если есть) — текущая фаза; часть проблем может быть «известна» или «запланирована»
- `ROADMAP.md` (если есть) — требования текущей фазы

## Phase 2: Сканировать кодовую базу

Использовать пути из `## Audit scope` → `Исходный код`. Прочитать все `.ts` и `.tsx` файлы в указанных директориях, а также конфигурационные файлы из `Конфигурационные файлы для проверки`.

## Phase 3: Анализ по 9 категориям

Собрать **все** находки прежде чем писать отчёт. Для каждой находки:
- категория + ID (CRIT-1, DOC-2 и т.д.)
- файл + строка
- что не так и почему это важно
- конкретное исправление

### 1. 🔴 Critical / Safety violations

Проверить каждый пункт из `## Safety-critical constraints` и `## Known constraints` в CLAUDE.md. Это блокеры — нарушение любого из них недопустимо.

Логика проверки: найти в коде все места, где выполняется операция, которую защищает каждый constraint, и убедиться что защита присутствует. Обходные пути (bypass) считаются нарушением.

### 2. 🟠 Противоречия с документацией

Сравнить фактическое поведение кода с документами из `Audit scope`. Для каждого описанного поведения: реализовано ли оно в коде? Для каждой ключевой функции кода: описана ли она в документации?

Если код расходится с документом, но намерение неясно — пометить как `[ambiguous]`, не исправлять автоматически.

### 3. 📋 Недокументированная логика

Найти в коде поведение и модули, которые **не отражены** в документации проекта:
- Файлы/модули, отсутствующие в разделе «Структура файлов» технической документации
- Маршруты API без описания
- UI-поведение или бизнес-правила, не упомянутые в продуктовой документации
- Env-переменные без описания в технической документации

Для каждой такой находки — **обновить документацию**: добавить описание в нужный файл. Это не ошибка кода, а пробел в документации.

### 4. 🔵 Логические ошибки

- Неверные условия (`>` vs `>=`, инвертированные булевы)
- Отсутствующий `await` на async-вызовах
- Необработанные Promise rejections
- Null/undefined dereference без guard
- Race conditions при обновлении state
- Ошибки в числовой логике (сумма ≠ слагаемые, неверные единицы, переполнение)

### 5. 🟡 Мёртвый / избыточный код

- Неиспользуемые переменные, импорты, функции, компоненты
- Дублирующаяся логика (одно и то же вычисление в 2+ местах)
- Закомментированные блоки кода
- Re-exports несуществующего
- Feature flags или ветки, которые всегда true/false

### 6. ⚡ TypeScript strict compliance

- Явный `any` тип
- Неявный `any` (нетипизированные параметры, отсутствующие return types у экспортируемых функций)
- Type assertions (`as T`) без обоснования
- `@ts-ignore` или `@ts-expect-error` без комментария
- Нарушения strict mode, которые поймает `tsc --strict`

### 7. 🏛️ Соответствие соглашениям

Проверить по правилам из `## Development conventions` в CLAUDE.md. Типичные нарушения:
- Неверный casing идентификаторов
- Несколько компонентов в одном файле
- Прямые сетевые вызовы в компонентах (если запрещены)
- Комментарии, описывающие «что», а не «почему»

### 8. 🔄 Импорты / зависимости

- Циклические импорты (A импортирует B, B импортирует A)
- Неиспользуемые импорты
- Импорты из несуществующих модулей
- Пакеты в коде, отсутствующие в `package.json`

### 9. 🐢 Производительность

- Тяжёлые вычисления или array-операции внутри JSX return (нужен `useMemo`)
- `useEffect` с отсутствующими deps (stale closure)
- `useEffect` с лишними deps (бесполезные re-renders)
- Отсутствие `useCallback` для функций, передаваемых как props дочерним компонентам
- Монолитные компоненты, рендерящие всё без условий

## Phase 4: Структурированный отчёт

Формат строго такой:

```
## Аудит кода — отчёт

### Сводка
| Категория | Найдено |
|-----------|---------|
| 🔴 Критические нарушения | N |
| 🟠 Противоречия с документацией | N |
| 📋 Недокументированная логика | N |
| 🔵 Логические ошибки | N |
| 🟡 Мёртвый / избыточный код | N |
| ⚡ TypeScript strict | N |
| 🏛️ Соответствие соглашениям | N |
| 🔄 Импорты / зависимости | N |
| 🐢 Производительность | N |
| **Итого** | **N** |

### 🔴 Критические нарушения

**[CRIT-1]** `src/features/planner/PlannerView.tsx:42`
> **Проблема:** ...
> **Почему важно:** Нарушение constraint #N из CLAUDE.md.
> **Исправление:** ...

### 📋 Недокументированная логика

**[DOC-1]** `src/features/someFeature/SomeComponent.tsx`
> **Проблема:** Компонент реализует логику X, которая не описана ни в одном документе проекта.
> **Действие:** Добавить описание в соответствующий раздел документации.

... (по каждой категории)

### ✅ Категорий без нарушений: [список]
```

Завершить отчёт:

> **Что исправить?** Напиши «всё», конкретные ID (CRIT-1, LOG-3, TS-2) или категорию («все TypeScript», «все критические»).

## Phase 4.5: Сохранить отчёт и запланировать проработку

Выполнить сразу после вывода отчёта пользователю, без дополнительного запроса — это стандартный шаг для каждого запуска аудита:

1. **Сохранить отчёт в файл.** Путь: `docs/audits/YYYY-MM-DD-project-audit-report.md`, где `YYYY-MM-DD` — текущая дата. Создать директорию `docs/audits/`, если её нет. Содержимое файла — тот же текст, что выведен пользователю в Phase 4 (сводка + все находки по категориям, дословно).

2. **Добавить пункт в `ROADMAP.md`** (если файл существует в проекте). Один короткий чеклист-пункт, ссылающийся на файл отчёта целиком — не разворачивать каждую находку отдельной строкой:
   ```
   - [ ] Проработать отчёт аудита кода `docs/audits/YYYY-MM-DD-project-audit-report.md` (N находок: M критических, ...)
   ```
   Куда вставлять:
   - Если в `ROADMAP.md` есть раздел «Технический долг» — добавить туда.
   - Если раздела нет — создать его перед разделом активной/текущей фазы (см. `STATUS.md`), не внутри чеклиста самой фазы (аудит обычно не привязан к скоупу конкретной фазы).

3. **Кратко сообщить пользователю**, что отчёт сохранён (путь к файлу) и пункт добавлен в roadmap — одним предложением, до или после ответа на вопрос «Что исправить?».

## Phase 5: Применить исправления

После того как пользователь указал что исправлять:

**Исправить автоматически** (без дополнительных вопросов):
- Неиспользуемые импорты и переменные
- Неверный casing идентификаторов
- Dead code (закомментированные блоки, недостижимые ветки)
- TypeScript: добавить типы там, где правильный тип очевиден из контекста
- Обновление документации для категории 📋

**Спросить перед исправлением:**
- Противоречия с документацией, где намерение неоднозначно (`[ambiguous]`)
- Любые изменения в safety-critical потоках
- Рефакторы, затрагивающие несколько файлов
- Изменения, где «исправление» может сломать что-то неочевидным образом

Формат вопроса:
```
⚠️ **[ID]** Не могу решить однозначно.
**Ситуация:** [что делает код vs. что написано в документации]
**Вариант А:** [соответствует продуктовой документации]
**Вариант Б:** [соответствует текущей логике кода]
Что выбрать?
```

После всех исправлений — краткое резюме: что исправлено, что пропущено, что требует решения пользователя.
